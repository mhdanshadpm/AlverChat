## Phase 3/4 commands, typing and read state — 2026-11-13 20:55

## Chunked file transfer (receiver pulls) — 2026-11-14 01:06

- The receiver pulls: it opens the session, sends `file_accept{resume_from}`, and only then does the sender stream, over that same connection. A pause, crash or reconnect costs nothing because the side that owns the part file also owns resume, and a sender never queues bytes nobody is reading.
- The transfer id *is* the attachment id *is* the message id, so a file bubble resolves its card through the primary key and no migration or new index was needed. Direction is derived from the message's sender (`local`), not stored on the attachment.
- Transfer frames are matched by `payload.transfer_id`, never by the envelope id. The core stamps a fresh id on every accept, chunk, ack and cancel, so only an offer — which the app builds itself — carries the transfer id in the envelope; comparing the two rejects every real peer.
- The database row is the user's intent and the in-memory `LiveTransfer` map is the driver's progress. A driver reads the row between batches and never writes it mid-run, or a `transferring` write would undo a pause the user clicked a moment earlier.
- Only `Transferring` keeps live progress. `Failed` is not terminal in the core state machine, so a stale entry would survive a failure; the map entry is dropped for every other state and a stopped download reports from its resume index instead.
- Progress reaches the UI through the existing `messages-changed` event, at most twice a second. A 500 MB file crosses thousands of batch boundaries and the shell already refetches the thread on that signal, so a new per-tick event would only add vocabulary and load.
- `push_accepted` and `SendRequest` exist because the desktop's session loop has already consumed the `file_accept` frame by the time it decides to stream; reading the accept twice would deadlock the session. The core keeps `push_chunks` as the one-call form for tests and other callers.
- Size policy comes from `platform::SettingsState::snapshot()` (settings.json), not the store's settings rows — those rows are never written, the same reason `send_announcement` reads the live settings. An empty `max_file_size_mb` falls back to `files::DEFAULT_MAX_FILE_BYTES` rather than rejecting every file.
- A re-offer of a known transfer resumes an `Accepted`, `Failed` or stale `Transferring` download, but leaves `Paused` and `Offered` alone: the sender's retry heals a broken pull without overriding the user's pause or a download nobody asked for.
- Pausing or cancelling a download that no driver is watching sends one advisory `file_cancel` on a short-lived session and ignores the failure. The peer's session loop deliberately sends no receipt for a cancel, and a peer that walked away must not turn a local button press into an error.
- Outgoing bytes stay in `<app-data>/outgoing`, incoming files land in the user's `downloads_dir` (default `<app-data>/downloads`), and the resume sidecar sits beside the part file so a moved folder carries the file and its resume state together. On-disk names come from `stored_name(id, file_name)`, so a peer cannot choose a path or overwrite another transfer.
- `send_file` takes the file as a base64 data URL and `open_attachment` hands the resolved path to `tauri-plugin-opener`: the picker keeps ownership of file access in the webview, and the shell never invents a filesystem handle.

## Developer secrets without the keychain — 2026-11-14 01:20 (superseded by "File-backed secrets by default" at 15:20)

- Secrets go through one `secrets::Secrets` store instead of three `keyring::Entry` calls, so the database key, the identity and the LAN passphrase cannot drift into different storage rules.
- `ALVERCHAT_DEV_SECRETS` swaps the keychain for `0600` files under the instance data directory, but only in debug builds (`cfg!(debug_assertions)`): the macOS prompt is really "this ad-hoc-signed binary is not the one that created the item", and a shipped binary must never be talkable into keeping keys in a file.
- A profile is refused when its store does not match its database, in both directions, with the fix in the message. Without it the first hatch run fails as "file is not a database" after quietly generating a key, and unsetting the flag afterwards would leave the profile unopenable.
- The hatch is documented with a scratch `ALVERCHAT_DATA_DIR`, because reusing the real profile is exactly the mismatch the guard refuses; two dev profiles also stop sharing one identity.

## Message latency — 2026-11-14 12:00

- macOS resolves a peer's mDNS name to its link-local IPv6 address before the IPv4 one, and a connect to that address stalls for the whole five-second timeout before IPv4 is tried. `connect_to_peer` now races every resolved address and keeps the first that connects, so a send is bounded by the reachable address instead of the unreachable one.
- One dialed session per peer stays warm for 30 seconds (`OUTBOUND_IDLE`), so a message, typing flag or receipt reuses it instead of paying another resolve, TCP connect and TLS handshake. The responder closes a silent session after 60 seconds, so the window stays inside that. Any send error drops the session and retries once with a fresh dial; a replayed envelope is harmless because the store dedupes by message id.
- The composer queues the message and returns: the bubble appears immediately as pending, and the outbox plus its retry loop own delivery. The status flips to sent through the existing `messages-changed` signal when the receipt lands, so the UI never blocks on a peer handshake.



## File offers reach the receiver — 2026-11-14 12:20

- An incoming `file_offer` was compared against the sender's peer id (`payload.chat_id != remote`), but the app builds `chat_id` as the *receiver* it addresses. Every offer was therefore rejected as "not theirs", the receiver closed the session without a receipt, and the sender retried forever with a bubble stuck at "Sending… 0%". The check now compares the payload's `chat_id` with this device's own peer id.
- The outbox retry loop used to exit whenever the peer had no endpoint, so an offer queued while discovery was between resolutions was never delivered. It now backs off (1 s → 60 s) and keeps watching the pending queue instead of breaking.
- A re-offer with no current endpoint no longer drops its delivery attempt: the retry loop owns the queued offer and delivers it when the peer reappears.
- Verified with two fresh profiles on one machine: two 615 KB offers were auto-accepted, pulled, blake3-verified and renamed into the receiver's downloads folder; both databases report `Completed` and both outboxes are empty.

## LAN passphrase enforcement and partial settings — 2026-11-14 13:16

- The passphrase challenge runs once after the authenticated handshake: each side sends `{nonce, mac}` where `mac` is the BLAKE3 keyed hash of `"alverchat-lan-v1\0{from}\0{to}\0{nonce}"` under the passphrase hash, compared in constant time. Mixed configuration (`Some`/`None` or different secrets) is refused in both directions with a message that names which side lacks a passphrase, so the failure is actionable instead of a silent stall. Verified between two scratch peers: with the passphrase on p3 only, the send stayed "Sending…" and each side logged its own refusal; once p4 saved the same passphrase the queued message delivered on outbox retry and was read.
- Changing or clearing the passphrase bumps `auth_epoch` and clears the warm outbound cache (`reset_authenticated_sessions`), and the inbound session loop compares the epoch on every frame. Without the bump, enabling encryption would leave already-open sessions carrying traffic under the previous policy — the toggle would only govern new handshakes.
- `update_settings` takes a JSON patch and overlays it on the stored settings (`merge_settings`), because the UI sends only the fields it changed. Deserializing the patch as a full `AppSettings` silently reset every other preference to its default: that is what wiped display names, pushed peers back into onboarding, and published fallback beacon names. A rejected patch (e.g. out-of-range opacity) fails before mutating state. Verified live: a theme toggle persisted `theme: light` while `displayName` and the rest stayed intact, and each peer's beacon updated to the real name ("Cy" / "Dia") without a restart.
- Clearing the passphrase returns the encryption toggle and the conversation footer to "Not encrypted — set the network passphrase", and a message sent afterwards delivered and was read, so the reset path is exercised in both directions rather than only at handshake.

## Phase 6 calls — 2026-11-14

- The Rust shell stays a signaling relay, not a call state machine: `send_call_signal` turns one webview signal into the protocol frame, enqueues it on the durable outbox, and `handle_signal` records the call log and re-emits the frame to the UI as `call-signal`. SDP/ICE bodies are opaque to Rust; media never leaves the WebRTC stack.
- Call frames ride the existing warm outbound session beside messages (whitelist extended by `calls::handled_kind`), so signaling inherits TLS, peer-key pinning, receipts and offline outbox retry for free. A missing endpoint queues the frame instead of dropping it — signaling may be the first frame after a reconnect.
- One live call at a time, and the caller is the only side that renegotiates (screen share, camera on/off): the receiver answers every offer. That avoids the perfect-negotiation glare machinery for a two-peer call.
- WebRTC runs with `iceServers: []` — host candidates only, LAN by construction, nothing leaks to a STUN server.
- Both the full app and the compact quick window mount their own `useCall` and listen to `call-signal`, so an incoming call rings in whichever surface is open; the call surface sits in an `overlay-hit` wrapper so the click-through hit regions keep working over the compact window.

## Heartbeat presence over warm sessions — 2026-11-14 13:40

- Presence is probed on sessions that already exist rather than by dialing the whole LAN: the beat pings each warm outbound session every 20 s, so a vanished peer is noticed in about 40 s, while peers we are not talking to keep mDNS removal as their authority. Dialing every discovered peer on a timer would cost one TLS + Noise handshake per peer per beat.
- A failed ping is retried once on a fresh session before the peer is marked offline. That separates a dropped socket from a dead machine: a live peer keeps its presence, and a dead one flips after two failed probes; any later inbound frame or beacon flips it back.
- `ping`/`pong` never touch the store, the outbox or unread counts; the pong echoes the ping id and reverses the route, which the unit tests pin. The receiver only replies, so ping and pong cannot cross on a bidirectional session pair.
- The macOS `msg_send!` calls in `set_dock_icon` needed `#[allow(unexpected_cfgs)]` under the current toolchain's check-cfg; without it `cargo clippy -D warnings` fails on macro-internal `cfg(feature = "cargo-clippy")` probes that the crate does not control.

## Decode fuzzing and protocol throughput — 2026-11-14 13:53

- Envelope decoding is now covered by proptest: arbitrary byte slices up to 2 KiB must return a `Result` (no panic), every known frame kind must round-trip its id, route, clock and kind, and any version other than 1 must return `UnsupportedVersion`. This is the layer a hostile LAN peer reaches first, before signature checks or Any storage.
- `crates/alver-core/tests/performance.rs` is `#[ignore]`d on purpose. It is evidence, not a gate: timing tests on CI runners vary enough to produce false failures, and the numbers only need to answer whether the JSON path is negligible next to TLS and SQLite.
- Measured on this Apple Silicon macOS host in a release build (2026-11-14): decode 0.93 µs/frame (1.07 M/s) for a 540-byte `message` envelope, encode 0.65 µs/frame, HLC tick+merge ≈3.7 ns/op, BLAKE3 over a 40 KiB chunk ≈1.6 GiB/s, `MessageLedger::apply` 0.36 µs/message. At these rates the protocol layer is two orders of magnitude cheaper than the per-frame AEAD and SQLite commit it sits beside.

## Peer read receipts — 2026-11-14 14:02

- Peer read receipts reuse the existing `receipt` envelope with `status:"read"` and a `message_ids` batch instead of adding a frame kind: the transport already had a validated, acked receipt shape, and a new kind would have meant another whitelist entry, another delivery path, and another loop hazard for no gain.
- Batches cap at 256 ids. A thread can accumulate thousands of unread rows, and one frame per message would turn opening a chat into a flood of handshakes; 256 ids stay far below the 1 MiB control cap even with UUID text, and the outbox retries each batch independently.
- The reader queues receipts on the durable outbox and drains them on a background thread, rather than sending them inline from `mark_as_read`: the UI's mark-as-read must stay instant, and an offline peer should get the receipt when it reappears, exactly like a queued message.
- The receiver checks ownership before recording: the id must resolve to a stored message in its direct chat with that sender and must have been sent by this device. `record_receipt` alone would accept any known id, which would let a peer mark another chat's messages read or forge receipts for messages it never received.
- An inbound `delivered` receipt is dropped without an acknowledgement. Delivery receipts are the answer to a frame on its own send session; answering one would create a receipt-of-a-receipt loop between two peers.
- Group threads produce no peer receipts: there is one read state per member and no single reader to attest, so the UI keeps showing the local read state while direct chats gain the double-tick source.
- Storage and transport use different names for this device: receipts are written with the reader id `local`, but the envelope route must carry the signed `identity.peer_id()`. The first live run stamped `from: local` and the peer correctly dropped every frame as an invalid envelope, leaving the sender on Delivered; the fix keeps `ME` inside storage calls only.
- `mark_as_read` deliberately does not emit `messages-changed`: the shell answers that event with another `markAsRead`, so emitting from the command would make an open thread reload itself forever. The sender's refresh comes from the inbound receipt frame instead, and only when a receipt actually advanced.

## File-backed secrets by default — 2026-11-14 15:20

- Secrets — the SQLCipher database key, the Ed25519 identity and the LAN passphrase — now live in `secrets/` under the instance data directory, one `0600` file per secret, on every platform and in release builds. `ALVERCHAT_KEYCHAIN=1` opts back into the OS credential store. The user asked for the keychain prompts to stop, and on macOS a keychain item belongs to the binary that created it: an ad-hoc-signed `tauri dev` rebuild is not that binary, so the dev build and the installed app — which share `com.alverchat.desktop` as their app-data directory and their `AlverChat` keychain service — spend every launch re-arguing about access.
- The trade is deliberate. A file protects the profile against anyone who cannot read your account, which is the same boundary the keychain enforces for an unlocked session; it does not survive someone with your home directory and no full-disk encryption. A keychain that gets denied does not fail that quietly — it either blocks the app or, in the old code, left a regenerated key holding an unreadable database.
- Migration replaces the two-way refusal: when the file is missing and the profile already has a `messages.db`, the secret is read from the credential store once, written into `secrets/`, and the keychain is never touched again. A fresh profile has no database, so it never opens the keychain at all — verified live with a scratch instance: two 32-byte `0600` files, `security find-generic-password` reporting no item for the instance, a silent start, and a restart that reused both keys untouched.
- Reading a key that the store refuses to give is an error, not a licence to generate a new one. Silently re-keying would leave `messages.db` permanently unopenable, so `copy_from_keychain` returns the failure with what to do about it: approve the prompt, or run once with `ALVERCHAT_KEYCHAIN=1`.
- The old mismatch guards went with it. They existed because a profile could be pointed at the wrong store; now one store is correct and the other is a migration, so both directions succeed instead of refusing.
- `secrets/` is the new name; a profile created while the file store was the developer hatch keeps its `dev-secrets/` directory (`file_store` prefers `secrets/` and falls back), and `secrets::tests::a_profile_keeps_the_store_it_was_created_with` pins that so a scratch profile's history stays readable.

## Backups carry the keys their database needs — 2026-11-14 15:45

- A backup is the profile, not just the rows: the payload moved to `version: 2` and now holds `databaseKeyBase64`, `identityKeyBase64` and `lanPassphraseBase64` next to the database bytes. Before this, `restore_backup` wrote a SQLCipher file encrypted with the *backing-up* device's key onto a device holding a different one, and the next start failed as an unopenable database — a backup that only works in place.
- That is safe only because the container is already Argon2id + XChaCha20-Poly1305 under the user's own passphrase, which is why the passphrase field now says the file also holds this device's keys. A v1 archive still restores: its database came from this device, so this device's keys are the right ones.
- The identity travels too, so moving to a new machine keeps the fingerprint peers already pinned instead of showing every contact as a stranger mid-conversation.
- A restore is checked before it is believed: after writing the keys and the database, `open_message_store` runs exactly the startup open, and any failure puts the previous `messages.db` and the previous secret files back and returns an error. Without that, the one command whose whole job is preserving history could leave a profile that will not boot.
- `forget_lan_passphrase` runs on the success path: the passphrase in the archive replaces the network secret the running process cached, and the next peer handshake should use the restored one rather than the old.

## Peer photos travel by hash, not by broadcast — 2026-11-15 00:03

- A photo is declared, not delivered. The heartbeat pong carries the blake3 hash of the photo this profile publishes, and only a peer whose cache disagrees asks for the bytes with `avatar_request{peer_id, have_hash}`. The alternative — sending every profile's photo to everyone, or embedding it in the peer list — puts 512 KiB of pixels on the network per peer for pictures most people never look at, and it would be a broadcast of someone's face rather than a reply to a request.
- The hash is also the verification. The receiver re-hashes the bytes it is handed and stores them only when they match the digest the offer declared, so a photo can only be the one the peer published under that hash; a mismatch keeps the copy already cached instead of replacing it with whatever arrived. The frame additionally has to name the peer that sent it.
- Privacy is one switch, not two. "Who sees my status → Nobody" withholds presence and the status line in the pong, so it withholds the avatar hash there too and refuses a direct `avatar_request` as well. The alternative — gating the declaration but answering the pull — would have made the setting readable only as a hint, and a request is exactly how a face would have been fetched around it.
- Withdrawal reuses the same field. An empty `avatar` in a pong means "this profile has no photo" and drops the cached copy, while an *absent* field means "an older build", which keeps whatever was cached; a peer that goes quiet therefore keeps showing the last photo it published, the same way its name does.
- `profile_update` stays unused on purpose. A peer's display name already reaches everyone through its signed beacon (and is re-advertised when Settings changes it), while presence, status and photo hash reach the peers that hold a warm session through the pong — the envelope kind would be a third copy of facts the network already carries.

## A peer's edit, unsend and reaction converge — but a peer's delete-for-me never does — 2026-11-15 00:24

- The three frames existed in `payloads::ALL_TYPES` and `classify` from the start, and the store has always kept revision rows and tombstones, so the gap was purely that the desktop never queued or handled them. Doing that locally meant the UI's own promises — "Delete for everyone", a reaction chip, an "(edited)" tag — were true on one device and false on the other.
- **The session is the actor, never the payload.** `reaction` carries no name and inbound edits and unsends are applied with the authenticated peer as the actor, so the rules already property-tested in `alver_core::rules` decide authority: only a sender edits their own message, only a sender or a recorded admin of the group that holds it unsends, and a tombstone stays a tombstone. Choosing the store as the authority instead of writing a second check in the desktop handler means the same code decides for a local click and for a peer's frame, and there is no way to forge a chip for someone else by naming them.
- **A frame about a message we do not have is dropped, not an error.** Retention, `clear_chat` and a chat left on one device can all leave a real peer with a message this one no longer has. **(corrected 2026-11-15 18:44 by item 44: only two of those three are live — `apply_retention` is a tested purge that nothing schedules, so the argument holds on `clear_chat` and a left chat alone, and the sentence was true only of a feature this build does not run.)** Refusing the session over that would turn an honest divergence into a disconnect, and the peer's retry loop would redial forever. Malformed payloads, an empty or oversized body, an emoji past 32 bytes and a clock more than five minutes ahead *are* errors, because they can only mean a broken build — and the clock bound is the one an incoming message already has, now shared through `clock_is_plausible`, so an "edit" cannot also be a way to move a message to a date that has not happened.
- **Delete-for-me does not travel.** `for_everyone: false` arrives as a no-op and this device never sends one. Applying a peer's personal housekeeping here would let any machine on the LAN erase a message from another device that never agreed to it, and the sender's own UI already says so ("This message disappears from this device only"). The field's serde default stays `true` in both directions: the durable reading is the safe one, and a defaulted-to-`false` frame would be silently discarded — the sender would think an unsend landed when it never left.
- **Reactions refresh through `messages-changed`, not a new event.** `Conversation.reload()` already re-reads every message's tally on a revision bump, so the existing event carries a chip as well as a body, and no second cache had to be invented for the one surface that draws chips. The bridge gained no method: the reading side was already complete, which is how the gap stayed invisible for so long.
- `(edited)` was drawn from a field the real app never set — `MessageDto` had no `edited`, so only mock mode could show the tag the boards specify. It now comes from the revision rows that an edit already writes, and stays false on a tombstone, whose bubble shows "This message was deleted" instead.

## Discovery has two paths, and each owns only the peers it can see — 2026-11-15 00:52

- The fallback was already promised before it existed: `UdpDiscovery` had been in `alver-core` since Phase 2, README and Settings both named UDP 47986, and `run_connection_test` reported that port as if it were open — while the only code that ever looked for a peer was the mDNS browse. A port number in a diagnostics screen is not a discovery path, so the beacon now leaves on both, and `ConnectionReport` says which one is live (`discoveryActive`) rather than quoting a number that might be a claim.
- **The fallback signs an address, not a hostname.** mDNS hands out `alverchat-<id>.local.` because the multicast that carried the beacon also resolves the name; a machine on guest Wi-Fi with client isolation, or behind a firewall that drops 5353, has no way to turn that name into a route — which is exactly the machine the fallback exists for. So each copy of the beacon is signed with the announcing interface's own literal address, one per usable adapter, aimed at that adapter's subnet broadcast (`255.255.255.255` only where the interface reports no broadcast, since the limited address leaves through the default route and may leave the subnet with it). Carrying the packet's source address instead was the alternative, and it is unsigned: the endpoint is inside the signature precisely so a beacon rewritten in transit stops verifying.
- **A datagram that is not a beacon is a non-event, not an error.** The discovery port is open to the whole subnet, so other software, truncated reads and tampered payloads all arrive. `receive_once` returns `None` for everything that does not parse and re-verify, and only a socket-level failure is reported — anything else would either end the loop that is the fallback's whole implementation or fill the log with somebody else's traffic. The self-filter is the other half of the same shape: a broadcast to `255.255.255.255` comes back to the sender and this machine's own beacon verifies, so the only thing that stops the app from listing itself as a peer is comparing the id.
- **Silence only counts for the peers nobody else is watching.** The heartbeat rule was already "a peer without a warm session is governed by mDNS removal"; the fallback needed its own counterpart or a vanished machine would stay online forever when mDNS is the broken path. So it keeps its own last-heard clock and expires a peer after five missed announcements — but not while the browse still lists that peer, and not while a warm session is already answering pings. Letting it expire everything would have been simpler and wrong: two instances on one host cannot both bind the port, so the one that lost it would be called offline by its own silence.
- **mDNS dying no longer takes discovery with it.** `start_peer_discovery` used to return the daemon's first error, which meant a host that refused multicast also skipped the heartbeat loop entirely. `DiscoveryState.mdns` is now `Option`, the browse thread only starts if it exists, and the broadcast path starts either way — two independent ways to be found, and a machine that lost one still gets discovered by the other.
- **One socket, bound once, degraded out loud.** The loop owns its socket for the life of the process rather than retrying the bind on a timer: a port held by a second instance or another tool will not free up on a schedule, and retrying would reprint the same line every few seconds. The cost is a machine that could not bind at startup keeps mDNS alone, which is the reason `udp_open` is published to Settings instead of left implicit.
- **"Visible on network" had to mean the same thing on both paths.** The setting already took the mDNS announcement down; announcing over UDP anyway would have made the switch readable only as a hint, and it is the one setting in this area whose whole promise is not being found. The broadcast loop asks the same flag before it sends anything.

## Every frame the app puts on the wire is now in the protocol table — 2026-11-15 00:58

- Item 28 ended with every wire kind checked against what the app actually writes, and `group` was the one that did not appear in `payloads::ALL_TYPES`. The table has been the protocol's single source of truth since Phase 1 and declares four per-change kinds — `group_create`, `group_update`, `group_member_change`, `group_icon_update` — which nothing in this build has ever sent. What it sends instead is a single `group` envelope whose payload is a bare signed `GroupState`. Both halves of the desktop agree with each other, so nothing was broken on this machine, which is exactly how the mismatch survived: sender and receiver invented the same private name.
- Left alone, it is an interop bug with a hard failure mode. `handle_peer_session` ends the connection on any kind outside its owned list, so a peer built to the documented table would have its session torn down by the reader the moment it sent a roster update — and a roster update is the only way a group exists on another machine. `docs/PROTOCOL.md` did not describe the frame either way, so there was nothing to contradict.
- **Reality was declared rather than the wire renamed.** The alternative — send `group_update` with the wrapped `{state: …}` payload the table describes — matches the doc better and breaks the installed 0.1.2 build next door: it would keep sending `group`, and the guard treats an unowned kind as fatal rather than ignorable. An accept-both alias was the third option and is the kind of shim that outlives the migration it was for. Mixed versions on one LAN are the real deployment here, so the frame stayed and the table moved.
- The new `GroupStatePayload` is `#[serde(transparent)]` over `GroupState` on purpose: the writer serialises the state itself, and a wrapper struct with a `state` field would have made the classifier describe a shape no peer ever receives. The desktop unit that closes this takes the bytes `deliver_group_state` produces — `GroupState::create` → `serde_json::to_value` → envelope — and asserts they classify as `Payload::GroupState`, so the two sides cannot drift apart silently again.
- The four per-change kinds stay declared. The classifier's contract is that an unknown type is ignorable, so a superset costs nothing at runtime, deleting them would rewrite the round-trip table for no behaviour change, and a future build that wants to say "member left" without resending a roster can pick one up. They are documented as superseded so the next reader does not send one into this build's fatal-on-unknown guard.
- Both directions are now pinned by a test, because a string literal in one process and a const in another have already proved they can disagree: every kind the session hands to a handler must be in the table, and every kind the table says this build owns must survive the reader's guard. The writer and the reader use the constant instead of the literal for the same reason.
- Adding the kind broke two core tests on the first run, and that was the finding: `crate::protocol::KNOWN_TYPES` was a second hand-written list of the same 33 names, mirroring `payloads::ALL_TYPES` by hand and asserted to match it only by behaviour. So the duplicate is gone — the framing layer now takes the declared table itself. It had already drifted once (this is how `group` ended up on the wire and off the table) and a list that has to be edited twice to add one frame will be edited once again.
- The same sweep over every `kind:` literal in the desktop found a second undeclared frame, and this one is the most security-relevant on the wire: `auth`, the LAN passphrase challenge, which is the first thing either side sends. It had no entry in the protocol table and no paragraph in `docs/PROTOCOL.md` — a handshake that exists only inside one function is not a protocol. It is now `AuthPayload { nonce, mac }`, with `mac` an `Option` because an absent or empty MAC is the meaningful "this device has no passphrase" case rather than a malformed frame, and the doc has a `## Session handshake` section covering the keyed MAC's exact pre-image, the reversed peer ids in the reply, the constant-time compare, the fail-on-both-ends rule for a half-set pair and the `auth_epoch` teardown. `hello`/`hello_ack` remain declared and unused, for the same reason as the four roster kinds.
- `handled_kind` now tests against a `OWNED_KINDS` array instead of a `matches!` list, so the drift test asserts over the same collection the guard reads. A test carrying its own copy of the list would have passed while the guard refused a frame. The session's core-answered kinds (`message`, `typing`, `ping`, `pong`, `receipt`) went from literals to the same constants the writer uses.

## Only an undeclared kind ends a session — 2026-11-15 01:24

- Item 29 fixed the direction it was looking at: "a frame this build sends must be declared". The other direction was worse than it sounded. Eleven kinds in `payloads::ALL_TYPES` are declared and have no handler here — `hello`, `hello_ack`, `bye`, `presence`, `profile_update`, `pin_update`, `sync_request` and the four per-change `group_*` — and the reader ended the session on all of them. A peer built from `docs/PROTOCOL.md` therefore lost its connection on its first advisory frame, and not only the advisory frame's feature: the session carries messages, files and calls, so a `pin_update` was a way to switch a peer off the network.
- The guard is now one pure decision with four outcomes (`frame_action` → handle, close, ignore, reject) instead of four set membership tests inside a loop condition, and `Reject` is reachable only by a kind the declared table does not contain. A version, `from` or `to` mismatch stays fatal — those mean a different protocol or a corrupt stream. "Unknown type is ignorable" was already the documented rule for the core classifier; the session now honours the same rule rather than contradicting the protocol one layer up.
- **Ignorable frames are acknowledged, not dropped quietly.** A durable outbox row retires on a `delivered` receipt, so an unanswered frame is retried on every reconnect forever. Item 27 already made the same call for a thread frame about a message this device does not have; the reasoning is the same one layer down.
- `bye` is the one frame that ends a session on purpose, and it needed both halves. Receiving it drops the peer's presence immediately instead of waiting for a 20-second probe plus a redial to agree a machine has gone; sending it happens on the two paths that actually exit the process (tray Quit and the in-app quit — closing the main window only hides it). It is deliberately not queued in the outbox: a farewell delivered later to a peer that is still here would end a session that should have stayed up. The mixed-version case is accepted rather than avoided — the 0.1.2 build has no handler and tears the session down on it, which is the outcome the frame asks for, and the process is exiting anyway.
- `hello` stays declared and unsent. It carries `supported_types`, which is exactly what this class of bug needed, but a capability exchange nothing reads is one more frame to get wrong; `frame_action` is the local answer to the same question and costs no wire traffic.
- Also in this pass: the reader's own kind comparisons were still literals (`"ping"`, `"pong"`, `"receipt"`, `"typing"`, the seven thread/avatar/announcement arms, `validate_receipt`, `is_matching_pong`), so item 29's claim held only for frames being written. Two doc references to a `serve_session` function that has never existed were corrected to `handle_peer_session` — and `is_matching_pong` was the one place where a silent rename would have kept passing tests, because the heartbeat unit still hand-builds a `"pong"` envelope on purpose: a reader test that imports the writer's constant proves nothing about the string on the wire.

## Pins are a shared list, so they now travel — 2026-11-15 01:30

- `pin_update` has been in the declared table since Phase 1, and `pins` has been a real table with a `position` and a `pinned_ms` just as long. Neither end was wired: `pin_message` wrote the row and returned the new list, and the session reader had no branch for the kind. A pin was therefore true on the device that made it, in a table whose schema has no author column — `pins(message_id PRIMARY KEY, chat_id, position, pinned_ms)` — which is what decided that the row is a property of the chat and not of the person who clicked.
- The outbound side is item 27's machinery reused rather than duplicated: `propagate_change(&app, &chat_id, frame::PIN_UPDATE, payload)` after the store write lands, so one durable outbox row per reader, retried on reconnect and retired by the ordinary `delivered` receipt. `pin_message` had to be restructured to drop its store guard before propagating, because `propagate_change` takes the lock itself — the same shape `react` already had.
- The inbound side needed a rule the other three thread frames did not. An edit or an unsend is checked by the store against the message's own author, and a reaction is written under the session peer's name, so those three are honest whatever chat they land in. A pin has no author to hide behind: it edits a shared list. So `handle_pin_update` requires the session peer to be one of that chat's readers, using `chat_audience` — the function the *sender* uses to choose recipients — and `shares_chat` is that symmetry written down: the set a change is sent to is the set allowed to send it. `handle_reaction` now applies the same check, because "my own name on a chip in a thread this peer was never in" was never a case anyone wanted.
- Two refusals and one acceptance, decided by what the wire can actually carry. `pinned` has a serde default, so a frame that omits it would read as an unpin; the handler refuses the frame instead, the same way the typing handler insists on its flag. The frame's `chat_id` is checked against the stored message's own chat rather than trusted. And the sender's `position` is taken as given: two devices pinning into one chat at the same instant can end up agreeing on the list and disagreeing on its order, and the next pin settles it. Ordering every writer against a clock to prevent a cosmetic difference would need a merge rule the table has no column for.
- `bye` and `pin_update` are now out of item 30's ignorable list, which is the outcome that list was written to make visible: a frame becomes ignorable because nothing has built the handler yet, not because the protocol says so. The drift test still walks the whole declared table, so a kind cannot go back to being fatal by accident.
- No front-end change was needed, which was checked rather than assumed. `Conversation.reload()` already re-reads `pinnedMessages` on `messages-changed`, so the pinned bar, its `N/M` tally and each bubble's pin marker update when a peer pins; Chat details re-reads its Pinned tab when the pane is reopened, which is how it already behaves for attachments and stars.

## A 1:1 thread has two names, and the reader resolves it — 2026-11-15 02:47

- `messages.chat_id` for a direct conversation is the id of the peer at the other end, which is the only rule that lets one table hold both a 1:1 thread and a group. It has a consequence nobody wrote down until now: the same chat is named differently on the two machines. Anu stores the thread under Bala's id and Bala stores it under Anu's — so every thread frame about a 1:1 chat arrives naming *the reader's own* id.
- `handle_reaction` and `handle_pin_update` looked that name up in the local store. On Bala's machine the lookup was for the thread called "Bala", which does not exist; the frame was malformed nowhere, the store refused it, the receipt still went back, and the outbox row retired. That combination is the worst kind of silent: the sender's UI shows the reaction delivered, and the receiver never shows it at all. `handle_message` had the same shape one layer earlier and had already been given the fix, which is why the message itself arrived while the decoration about it did not.
- The rule is one function — `thread_chat_id(named, my_id, remote)` — a frame that names nothing or names *us* is about the thread with the peer we heard it from, and anything else passes through unchanged. Group ids are the same string on every device, so they take the pass-through branch, and a frame naming a third peer keeps that id rather than being quietly redirected onto the current session's thread: the refusal has to be visible as a miss, because silently retargeting a stranger's message is how a wrong thread becomes a plausible one.
- Placing the fix on the reader rather than the sender was deliberate. The sender could have rewritten its own `chat_id` into the recipient's spelling, but a sender does not know how the recipient names things — a peer that has never discovered us has no row at all, and a group has one id shared by many readers. The reader is the only side that owns its own table.
- `thread_chat_id_tests` asserts all three branches from both seats (the same frame resolved by Anu and by Bala has to land in each one's own thread), the group pass-through, and both edge cases: an empty name and a foreign one.
