# Architecture

```text
packages/ui  ->  packages/bridge (PlatformBridge)  ->  apps/desktop (Tauri)
                                                ->  crates/alver-platform
                                                ->  crates/alver-core
```

`alver-core` has no Tauri or OS dependencies. `alver-platform` owns OS services. UI components use the bridge contract; `emptyBrowserBridge` is a browser-development adapter without peer data, and its message-send operation fails explicitly.

## Implemented foundation

- Versioned protocol envelope, hybrid logical clock, peer-key fingerprint/signatures, idempotent in-memory ledger, sender-only tombstones.
- Ed25519 install identity primitive, Argon2id LAN key derivation, XChaCha20-Poly1305 payload helper.
- Admin-signed group roster state with canonical member ordering, epoch checks, immutable Everyone-group roster, and atomic persistence in the SQLCipher store.
- Sender-only message edits with revision history, sender-only permanent tombstones, and FTS removal when edited/deleted.
- Local FTS search quotes user terms and caps query length, term count, and result count; edits replace indexed text and tombstones remove it.
- File receive primitive validates peer-supplied names and size, bounds chunk size/offsets, writes under an internal transfer ID, and checks BLAKE3 before finalizing.
- Encrypted backup container uses a fresh Argon2id salt and XChaCha20-Poly1305 nonce per archive. `create_backup` seals the settings, the raw `messages.db` and the secrets that key it (database key, device identity, LAN passphrase) into `<data>/Backups/*.alverbak`; `restore_backup` accepts only a file from that folder and re-opens the store before it commits, rolling the previous files back if the archive does not match.
- SQLCipher-backed SQLite open/migration with peers, chats, messages, FTS and an idempotent persistent outbox API.
- Desktop opens the SQLCipher message store under the app data directory and obtains its database key from `secrets/` beside it; message history is read in chat-clock order and survives restart.
- The desktop app loads a stable Ed25519 identity from that same file store, publishes signed mDNS announcements and the same beacon as a signed UDP broadcast, rejects malformed or invalid signatures, and emits verified discovered peers to the UI.
- Tauri 2 main window, CSP, native dock/compact/menu windows, drag/position commands, overlay hit testing, and an update check/install/relaunch flow backed by signed GitHub Release artifacts. The install half is the two-line `installAndRestart` in `packages/ui/src/updater.ts`, ordered so a failed signature verification ends the sequence before the restart; the macOS artifact in that flow comes from the `app` bundle target, not the `dmg`, which `release_config_tests` now insists on (PROGRESS item 49). The endpoint itself is not a hard-coded upstream URL at release time: `.github/workflows/release.yml` runs `node scripts/configure-updater.mjs`, which rewrites `plugins.updater.endpoints` from `GITHUB_REPOSITORY` before the build so a fork's clients ask that fork's feed, and the same test module requires the matrix, the bundle targets and that step's position in the workflow to agree (PROGRESS item 52).

## Network messaging status

The desktop messaging slice listens on a bounded TCP port, authenticates signed Ed25519 identities via TLS 1.3 `tokio-tungstenite` and Noise XX handshake, pins peer keys, encrypts message frames, stores outgoing messages in the SQLCipher outbox before delivery, retries offline messages, and stores received messages before acknowledging them. Signed mDNS announcements provide peer endpoints and identity keys.

Group fan-out, announcements with acknowledgements, call signalling plus WebRTC media, heartbeat presence over warm sessions, batched read receipts for direct chats, peer profile sync and backup/export/restore are connected to desktop commands. A peer's name arrives in its signed beacon, its presence, status line and photo hash in the heartbeat pong, and the photo itself is pulled by hash in `avatar_request`/`avatar_data` frames — so the `profile_update` envelope kind stays unused. Edits, delete-for-everyone, reactions and pins now converge too: `message_edit`, `message_delete`, `reaction` and `pin_update` are queued per reader of the chat in the durable outbox and applied inbound under the store's own authority rules, while a peer's delete-for-me is dropped. `typing` is addressed to that same per-chat audience rather than to the chat id, which is the only way a group can receive it, and a message that Forward copied says so through the `forwarded` key of its `message` frame (see `docs/PROTOCOL.md`). Peers are found by mDNS and, when multicast is blocked, by the same beacon broadcast over UDP 47986 — two independent paths, each with its own rule for when silence means a peer has left (see `docs/PROTOCOL.md`). Group threads keep per-device read state instead of peer receipts, and group calls are out of scope; the remaining unavailable actions are capability fallbacks — clipboard write, media capture on a device with none, and every peer path in the browser adapter. File transfer is connected: the receiver pulls `file_chunk` frames over an authenticated session and verifies the whole file by blake3 (see `docs/PROTOCOL.md`). Browser development uses an empty adapter and never fakes message delivery. Native overlay behavior, code signing, and notarization still need release-platform validation.

## Events between the two halves

Rust never calls a React function and React never reads the store, so everything that happens without the user asking for it crosses this boundary as a named event. Nine names exist, and each has exactly one kind of consumer:

- `overlay-state` — the whole dock snapshot; the main window's rail and the dock, compact and menu windows all repaint from it.
- `messages-changed{chat_id}` — the one signal for "this thread is not what you last read", raised by a send, an inbound message, a peer's read batch, a thread frame, an announcement and its acks, a transfer's progress, a group joined or left, and a chat cleared. The main window and the overlay windows both refetch on it, so no screen holds a private copy of a thread. The payload is a *thread* id and never a device id, which is a rule rather than an observation: the shell compares it with the open chat before clearing unread, and the compact rail compares it with its group rows. The one raiser that could not read it straight off its own argument was the outbox flush, whose row is addressed to a member even when the frame belongs to a group, so `frame_thread` now resolves it — the chat the payload names, else the chat the store holds for the message the frame names, else the recipient, which is the thread only for a direct row.
- `navigate-chat{chat_id}` — a tray or bubble click that must bring a specific chat forward.
- `settings-changed` — Rust wrote the settings file; the front end drops its cached copy.
- `hotkey-error{combo}` — the OS refused a shortcut, so the app rolled back to the default and says so.
- `message-alert{sound}` — Windows routes a received message to the dock bubble instead of a toast, and this frame is the chime's permission.
- `call-signal{…}` and `calls-changed` — the first carries a peer's WebRTC frame to the call engine, the second refreshes the history.
- `avatars-changed{peer_id}` — a peer's pong declared a different photo hash, so the cached face for that peer one is dropped and the surfaces still on screen pull the new one.

The list is short, stringly typed and therefore exactly the kind of contract that rots quietly: an event Rust stops emitting leaves a screen frozen until reload, and an event nobody listens for is a payload dropped on the floor. `event_wiring_tests` reads the sources on both sides and asserts the two sets are equal, in both directions.

The other half of the boundary runs the other way, and it is matched by strings too. React asks for work with `invoke('send_message', { chatId, text, replyToId })`, and Rust is told which of those names exist by one `generate_handler![…]` list in the shell; the argument object is then deserialized into the command's parameters by name, a Rust `reply_to_id` being looked for as `replyToId`. Nothing in either language's type system connects the two — `invoke` takes `string` and an untyped record — so a name or a key that drifts is not a compile error but a call that fails when a user presses the button. `command_wiring_tests` reads both halves as text and asserts four things: every invoked name is registered, every registered name is invoked, every key a call sends names a parameter of that command, and every parameter of a called command is either sent or of a type Tauri injects — `AppHandle`, `State<…>`, `Manager<…>` or `WebviewWindow`, which are the only ways a command can be callable with fewer arguments than it declares. Seventy-three commands and seventy-three call sites today, all of them written in `packages/bridge/src/tauri.ts`, which is the only front-end file that calls `invoke`; the walk covers `packages/ui` as well so that a second caller cannot appear unnoticed. Like the event guard it refuses to guess: a handler entry, a parameter or an argument it cannot read makes the test fail with the file and the text, because a scan that quietly skipped a call site would report a clean seam it had not seen.

## Two tables hold a value, and only one of them decides

There are three places this app persists something small, and which one is authoritative has to be said out loud because they are not interchangeable:

- **`settings.json`** is what the user sets. `platform::AppSettings` is the schema, `platform::SettingsState` the in-memory snapshot, and `platform::persist` the only writer — reached from `update_settings` (the settings patch command), from `set_hotkey` and `set_launch_at_login`, from the passphrase save, and from a restore. The rule that matters is *where* the number is read: at the moment the behaviour is decided. The file-size policy comes from `file_transfer::policy` reading the live snapshot, the announcement gate from `send_announcement` reading it, the edit window from `edit_message_local` handing it to `store.edit_message_within`, and the dock corner from `overlay-settings.json` at startup plus the `screen_corner` command while running. Nothing mirrors a `settings.json` field into a database row, which is what keeps the two from being able to disagree — item 43's LAN-encryption badge is the case where the mirror would have been a lie, because the flag is derived from the saved passphrase (the passphrase save and the startup load are the two places that recompute it) and not chosen.
- **SQLite `settings`** is a key/value table of *per-object* state, not preferences: `group.description.<id>`, `group.icon.<id>`, `group.left.<id>` and `attachment.duration.<id>`. All four have a writer and a reader in desktop commands, so the thread's voice-note length and the "you left this group" flag survive a restart without a column each. The same table also carries `alver-core`'s eight well-known keys (`setting::EDIT_WINDOW_MS` and friends), which are the *library's* override surface: every one has a reader in the crate, and the desktop writes none of them, so an embedding caller can set a budget the compiled default would not have chosen. `every_declared_setting_key_is_read_in_this_crate` keeps that promise checked.
- **The OS secret store** (a `0600` file unless `ALVERCHAT_KEYCHAIN=1`) holds the passphrase and the identity key. It decides `lan_encryption`, which is why that row is a status and not a switch.

A value therefore has one home and one decision point. When a preference looks like it needs both, the honest reading is that one of them is decorative — which is how items 43 and 44 found what they found. Item 45 ran the same two questions over the *columns* of every table instead of the keys of one, and item 48 over the forty fields of the other table — the `settings.json` struct, where the same `#[serde(rename_all = "camelCase")]` rule means every field has two spellings and only one reader per pane, and the answer is a list rather than a rule: nine columns are written and never read by any production query, one of them (`peers.trusted`) is written as the constant `1`, two (`groups.name`, `groups.epoch`) are a second copy of what the signed `GroupState` blob already decides, and one (`pins.pinned_by`, migration v7) is the column that was missing when a shared list attributed every pin to the device looking at it.
