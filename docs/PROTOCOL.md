# Protocol v1

Every control frame uses an envelope:

```json
{"v":1,"id":"<uuidv7>","type":"message","from":"<peer-id>","to":"<chat-id>","hlc":{"physical_ms":0,"logical":0},"payload":{}}
```

Unknown envelope types are ignored. Control JSON is capped at 1 MiB. Signed mDNS discovery beacons bind the peer ID and advertised endpoint. The desktop carries message envelopes over an authenticated TLS 1.3 `tokio-tungstenite` session and Noise XX session with pinned Ed25519 identities and bounded encrypted frames.

The ignoring half has a boundary worth knowing exactly, because a session is not a place to be strict by accident. The desktop reader classifies every received frame into one of four actions — handle, close, ignore or reject — and **only a kind the declared table does not contain is a reject**. A kind the table declares but this build has no handler for is acknowledged and dropped: the protocol's own rule for a frame the receiver cannot read is that the receiver ignores it, and tearing the session down instead would let one advisory frame take a peer's messages, files and calls with it. Rejecting stays reserved for what genuinely means "different protocol": an unknown kind, a wrong version, or an envelope that names the wrong peer. `frame_table_tests` pins both directions — every handled kind is declared, and no declared kind is a reason to drop a session.

Acknowledging an ignorable frame is not a courtesy; it is what stops the sender retrying it. A durable outbox row retires on a `delivered` receipt, so a silent drop would leave a peer re-sending a `sync_request` on every reconnect forever.

## Saying goodbye

`bye{reason}` is the one frame that ends a session on purpose. A device writes it to every warm session it holds as the process exits — from the tray's Quit, from the in-app quit, and from the run loop's own exit request, which is how Cmd+Q and the Dock's Quit leave; a farewell sent twice on the two paths that already said it travels on the session that is closing anyway and is not visible to anyone. It is never queued through the outbox, because a deferred farewell would eventually be delivered to a peer that is still here. The receiver takes the sender's presence down immediately rather than waiting for a probe and a redial to agree that a machine has gone. Nothing about the reply is waited for: the sender is leaving, and a session that is already dead is not an error at that point. A process that is killed rather than quit — `SIGTERM`, a crash, a logout that does not run the exit path — sends nothing, and its peers come down on the heartbeat TTL alone.

`hello` and `hello_ack` are declared and documented and this build neither sends nor needs them. Sending one would be the same mistake in reverse — a peer that has no handler for it now ignores it, which is right, but a capability exchange nobody acts on is not worth the frame. `sync_request`, `presence`, `profile_update` and the four per-change `group_*` kinds are in the same position: declared, ignorable, and superseded by the heartbeat pong and the bare `group` roster frame.

## Session handshake

Before any traffic, both sides of a session send one `auth{nonce, mac}` frame: a base64 32-byte nonce chosen by the sender, and a BLAKE3 keyed MAC — key `blake3(passphrase)`, message `"alverchat-lan-v1\0" + from + "\0" + to + "\0" + nonce` — or `mac: null` (or `""`, which is treated the same) from a device that has no passphrase. Each side recomputes the MAC for the nonce it was given, with the two peer ids in the opposite order, and refuses a reply that names anyone else. A half-set pair therefore fails on both ends rather than silently downgrading to open traffic, and changing or clearing the passphrase bumps `auth_epoch`, which ends every session opened under the old policy. The comparison is constant-time.

The frame is exchanged on the authenticated transport, so it authenticates a *policy*, not the identity: the pinned Ed25519 key established during the Noise handshake is what says which peer this is, and the passphrase is what says whether both operators meant to be on the same LAN.

## Group rosters

A roster change travels as one `group` frame whose payload is the signed `GroupState` itself — id, name, epoch, admin, members, admin public key, signature — not a wrapper object. One envelope shape covers a create, a rename, an icon change and a membership change, because the state carries its own epoch and signature; the four `group_*` kinds in the declared table are the older per-change split and nothing in this build sends one.

The admin is the only signer, and a roster always contains its admin, so the frame goes to every member of the new roster *and* every member of the previous one — the peers a change removed are exactly the peers that need to hear it — each from its own durable outbox row. A receiver accepts it when the signature verifies, the session peer is the state's own admin, the id is not `everyone`, and `verify_successor_of` passes against the last state it kept; an identical repeat is acknowledged and dropped, a stale or epoch-skipping update ends the session. The built-in `everyone` group rejects roster mutation on both sides. Accepting a state that no longer contains this device is what removes the group from the rail, and a later epoch that adds it back clears that.

## Discovery

A peer is found by one of two paths, and both carry the same `PeerBeacon`: version, peer id, display name, host, TCP port, public key and an Ed25519 signature over exactly those fields. Because the endpoint is inside the signature, a beacon that was rewritten in transit fails `verify()` and is never dialed.

mDNS is the primary path: the beacon is published as service text records and browsed, and the host it names is the `.local.` address the multicast itself resolves. The fallback repeats the beacon as a UDP broadcast on port 47986 every three seconds — one datagram per usable adapter, aimed at that adapter's own broadcast address, and signed with that adapter's literal address as its host. A peer that cannot run multicast is exactly the peer that cannot resolve a `.local.` name, so the address the fallback signs is the one it can route to.

Three rules keep the fallback from inventing anything. A datagram is not authenticated by its arrival: it is acted on only after `verify()`, and anything else — other software on the port, a truncated read, a beacon whose host was rewritten — is ignored rather than treated as an error, because ignoring is what keeps the loop listening. A broadcast sent to `255.255.255.255` comes back to the sender, so a beacon naming this machine's own peer id is dropped before it can list yourself as a peer. And "Visible on network" is honoured on both paths: hiding takes the mDNS announcement down and stops the broadcast, so a profile that asked not to be found is silent on every port it owns.

Presence is owned by whichever path is watching a peer. mDNS removal takes down the peers it lists and heartbeat takes the peers this device holds a warm session to, so the fallback only calls a peer offline when it is the sole path to that peer and has heard nothing for fifteen seconds — five missed announcements. A peer that is merely repeating on the wire does not re-trigger the outbox retry; only a sighting that is new, or old enough to have been dropped, does.

## Heartbeat presence

`ping{}` and `pong{ping_id}` ride an existing authenticated session; neither is stored, receipted or retried. The pong reverses `from`/`to` and echoes the ping envelope's `id` as `ping_id`, so a stale or crossed reply is rejected. A beat probes each warm session every 20 s and redials once before the peer is marked offline; peers without a warm session stay governed by mDNS removal.

A pong may also carry `presence` (one of `online`, `away`, `busy`) and `status` (the free-text status line) — the two things Settings → Privacy & Network calls "Who sees my status". Only an explicit "Nobody" withholds them, and it withholds those two fields alone: `ping_id` always travels, so hiding a status never hides that the machine is reachable. A receiver treats an undeclared pong like an older build's and falls back to its own liveness copy, and a declaration is dropped the moment the peer goes offline rather than kept as a state for a machine that is gone.

The pong carries a third field under the same gate: `avatar`, the hex blake3 hash of the photo this profile publishes, empty when it publishes none.

## Peer avatars

A photo is not a field of the peer list — it is up to 512 KiB of pixels, so it is declared by hash and pulled on demand, never fanned out to the network. The reader compares the hash a pong declares with the copy it already caches and, when they differ, queues one `avatar_request{peer_id, have_hash}` in the durable outbox. The owner answers with `avatar_data{peer_id, hash, media_type, width, height, bytes}` — the same envelope over the same authenticated session, and an empty body when it has no photo or the requester already holds the current one.

Three rules make the exchange safe without a new trust mechanism. A frame is refused when it names a peer other than the session that carried it. The owner honours "Nobody": a profile that withholds its status withholds its face, so a direct request is not a way to read what the pong would not say. And the receiver re-hashes the bytes before caching them, so a photo is stored only when it matches the digest the offer declared; a mismatch keeps whatever was cached before.

Withdrawal is a hash, not a delete. A peer that removes its photo declares an empty `avatar`, which drops the cached copy immediately — the other side never has to ask, and a peer that simply goes quiet keeps showing the last photo it published, because an absent field is what an older build's pong looks like.

## Read receipts

`receipt{message_id, status:"delivered"}` is the acknowledgement every accepted frame gets over the same session that carried it; it is never stored, retried or answered, so it cannot loop. Read receipts reuse the same envelope kind with `status:"read"` and `message_ids:[…]`: the reader batches the peer's messages it just cleared (at most 256 ids per frame), queues each batch in the durable outbox, and the peer acks the batch like any other frame. The receiver accepts an id only when the stored message lives in its direct chat with that sender and was sent by this device; unknown, foreign or group ids are dropped. A group thread has one read state per member, so it produces no peer receipts.

## What a message frame carries

`message{text, chat_id, reply_to, forwarded}` — four keys, each of them there because the receiver has to rebuild something the sender's screen already showed.

`text` is the body. A frame without it is fatal to the session, like the other refusals listed under *Thread convergence*, and it is the reason the declared table names `text` and not an older `body`: a table that describes keys nobody sends is a table that ignores every message on the network. `chat_id` is the chat as it is named on the *sender's* machine, which in a direct thread means the receiver's own id and is what `thread_chat_id` exists to read back. `reply_to` is the quoted message's id; it is kept only when it resolves to a real message in the chat the frame lands in, so a pointer to something the reader has not got simply stores an ordinary message. `forwarded` records that this body is a copy of something the sender received from elsewhere.

That last key is the only one of the four with no alternative source. A copy keeps the original's id nowhere — the forwarded message is a new message, written to a new chat, by the device that copied it — so without the flag the receiver sees a bubble that looks authored on the spot, and "who wrote this?" becomes unanswerable one hop later. The Forward action sets it, it is stored in its own column, and it is what the chip inside the bubble reads. A frame from an older build carries no key at all, and the one honest reading of an absent key is an original: refusing such a frame would break a network where half the machines can forward and half cannot even say they did.

## What an announcement frame carries

`announcement{announcement_id, group_id, text, created_ms, admins_only}` — one frame per member of the group's roster, each addressed to that member and each naming the group inside the payload.

`text` is the body, under the key both ends of the path have always used. The declared table named it `body` until 2026-11-15, which is worth recording for what it says about the table rather than about the wire: an announcement frame arriving on this network was refused by `classify` and reported as `Ignored{reason: Announcement}` every day it was wrong, and nothing broke, because the router dispatches on the *kind* and the handler reads the keys itself. So the table was not a gate — it was a description that had stopped matching the thing, and a size bound inside it (`text` longer than `MAX_BODY_BYTES`) was measuring a field no frame has ever carried. The frame table test round-trips the struct through itself, which cannot see this class of error at all; the guard that now exists builds the envelope with this build's own writer and hands *that* to `classify`.

`group_id` is the same string on every device, which is why an announcement needs no reader-side resolution like `thread_chat_id`. `admins_only` is not a hint: `check_announcement_authority` runs on the sending side before any frame is queued and again on the receiving side against the roster the reader holds, where a violation ends the session rather than storing the post — fail closed, because an announcement is a claim about a group's state and the claim is the peer's, not the reader's.

## Typing indicators

`typing{typing}` is advisory and deliberately not durable. It goes straight down the live session and never through the outbox, because a flag that finally arrives after the person stopped typing is worse than one that never arrives at all; it is acknowledged with the ordinary `delivered` receipt like any other accepted frame, and a peer that does not know the kind ignores it.

The audience is `chat_audience`, the same rule that decides who receives a reaction, a pin or an edit — the roster of a group, the one peer at the other end of a direct thread, everybody this device has discovered for the built-in Everyone group, and never this device itself. That is what makes a group indicator work at all: sessions are keyed by device, so a group id is not something a frame can be addressed to, and a typing flag sent to the group itself reached exactly nobody while looking like it had been sent.

A receiver sets the flag on the peer its session is with, not on the chat the sender named, and lets it lapse after six seconds without another frame — so a lost `false` retires the indicator on its own instead of stranding it. A group row has no session and therefore no flag of its own; it borrows one from its roster, which keeps the one honest rule in place: a group says "typing…" exactly when somebody in it does.

## Thread convergence

`message_edit{message_id, body, clock}`, `message_delete{message_id, for_everyone, reason}` and `reaction{message:{chat_id, message_id}, emoji, remove}` turn a change one device made to an existing message into a frame for the rest of the chat. They are queued in the durable outbox — one envelope per reader, freshly identified — so a reaction made while a peer is offline still arrives when it reappears, exactly like a message.

The audience is the chat, not the network: one frame to the peer at the other end of a direct thread, one per member other than this device in a group. Recipients acknowledge each frame with the ordinary `delivered` receipt, which is what retires the outbox row.

A direct thread has two names, and a frame about it has to be read with that in mind. Each device stores a 1:1 chat under the peer id of the device at the other end, so the same conversation is called `Bala` on one machine and `Anu` on the other, and a thread frame about it therefore always arrives naming *the reader's* own id — the name the sender read out of its own store, which is us as seen from there. `thread_chat_id(named, my_id, remote)` is the single rule that turns that back into the chat to update: a frame that names nothing, or names us, is about the thread with the peer we heard it from, and any other id passes through unchanged, because a group id is the same string on every device. It is applied to `message`, `reaction` and `pin_update`; an edit and an unsend name only a message id and never needed it. Comparing the name as it stands is how a reaction or a pin could be acknowledged, retired from the outbox and still never appear.

Three refusals decide what a peer's frame is allowed to do here.

- **The session is the actor.** A reaction frame carries no name; the chip is written under the id of the authenticated peer that sent it, so a peer can only ever add or remove its own.
- **The store decides authority.** An edit is applied with the session peer as the actor, so the existing rules — only the sender edits their own message, and never a tombstone — refuse a forged or resurrected one. An unsend goes the same way: the sender's own message through the ordinary path, otherwise only through the group-admin rule this device applies to itself, which needs a recorded admin of the group that holds the message.
- **A refusal to converge is not a fault.** A frame naming a message this device does not have — cleared by the user, left behind in a chat this device exited, or never received — is dropped and still acknowledged, because two histories that diverged should keep talking. (Age-based purging is *not* one of those causes in this build: `apply_retention` exists and is tested, and nothing schedules it — PROGRESS item 44.) The exceptions are the ones that can only mean a broken build: a malformed payload, an empty or over-long body, an emoji outside 32 bytes, or a replacement clock more than five minutes ahead, the same bound an incoming message is held to.

The edit window gates the device writing the edit, never the one receiving it. `Settings → editWindowMinutes` is read from the live settings snapshot at the moment `edit_message_local` decides, so the number that stops a late keystroke here is the number set here; an inbound `message_edit` is checked only for authority, because the sending device is the only one that knows how long it allowed its user to edit, and refusing it on the receiver's clock or the sender's clock would leave the two copies permanently divergent with no frame to repair them. Both sides of that rule are the same store arithmetic, but only one implementation of it runs. The live decision is `edit_message_within`, called from `apply_local_edit` (`apps/desktop/src-tauri/src/main.rs:2189`) with the window `edit_window()` at `:2157` builds out of the minutes the desktop read from `settings.json`, and the inbound handler calls `Store::edit_message` (`crates/alver-core/src/storage.rs:752`), which checks authority and no clock at all. `edit_message_in_window` (`crates/alver-core/src/store_ext.rs:1346`) is a second implementation of the same decision that nothing in this product calls: it takes its window from `Store::edit_window()` (`:1113`), which reads the `message.edit_window_ms` row (`setting::EDIT_WINDOW_MS`, `:33`) — and every writer that row has anywhere in this repository is a test: `store_ext.rs:2123`, `:2261` and `:2301` seed it with 60 000, 500 and 0 ms, `crates/alver-core/tests/migrations.rs:210` seeds it with 900, and `store_ext.rs:2328` deliberately leaves it absent to prove what the default then does. Unwritten, it resolves to `DEFAULT_EDIT_WINDOW_MS`, a 24-hour window (`crates/alver-core/src/rules.rs:16`), against the 15 minutes the Settings screen defaults to (`apps/desktop/src-tauri/src/platform.rs:108`). That is two numbers naming one rule, one of them unreachable from any build a user can run, and it is a trap for whoever reads the crate rather than the desktop: `alver-core`'s own declared-key guard cannot catch it, because the guard proves a key is *referenced* by non-test code and `EDIT_WINDOW_MS` is referenced, from `edit_window()` itself, which is the dead half (`store_ext.rs:2241-2249`). `transfer_policy()` (`:1135`) is the same shape beside it — a store-row reading of the file size limits with no product caller, because `file_transfer::policy` builds them from `settings.json` instead. Both stay: `alver-core` is a published boundary, and the helpers are what its `edit_window()` and `transfer_policy()` accessors are tested against. Recorded as library debt, not as behaviour — the window a device actually enforces is the Settings number, never a store row.

`pin_update{chat_id, message_id, pinned, position}` is the fourth frame of this kind, and the only one whose subject is a shared list rather than a message. `pins` is keyed by message and, from migration v7, also records who asked: the frame carries no author field because it does not need one — the authenticated peer on the other end of the session *is* the author, and `handle_pin_update` stores that id while `pin_message` stores this device's own. A pin that never crossed the wire left two devices holding two different lists while both looked right, which is why the frame exists at all; and before the author column existed the list attributed every row to whichever device was reading it, which is a claim about a peer that this device has no way to make. It is queued and acknowledged exactly like the other three, and a frame that omits `pinned` is refused outright, because that field is the whole point of the frame and a default would read as an unpin.

Two rules keep it honest. The receiver's authority is membership, not the payload: `chat_audience` is computed from the chat the *stored message* is in, and the session peer must be one of its readers — the same set the outbound side sends to, read in the other direction. And the sender's `position` is taken as given, so two devices pinning into one chat at the same moment can agree on the list and differ on its order until the next pin settles it; that is a cosmetic difference in a shared list, which beats keeping a private copy nobody is told about.

`for_everyone: false` is deliberately not applied. Delete-for-me is a claim about the sender's own history, and honouring it would let any peer erase a message from a device that never agreed to it — so this device never sends one, and drops it if it arrives. A frame that omits the field defaults to `true`: the durable reading is the safe one, and a silently ignored unsend would leave the sender believing it landed.

## File transfer

The sender stages the bytes and enqueues one `file_offer{transfer_id, chat_id, file_name, size, blake3_hash, note}`; it carries no file data. The receiver answers on a fresh authenticated session with `file_accept{transfer_id, resume_from}`, and the sender streams `file_chunk{transfer_id, index, bytes}` in a window of four, each batch answered by `file_ack{transfer_id, contiguous_index, complete}`. `file_cancel{transfer_id, reason}` ends a paused (`paused`), cancelled (`cancelled`) or refused transfer.

- Every frame names its transfer in `payload.transfer_id`. The envelope `id` is the frame's own id, except for an offer, which the desktop builds with the transfer id so outbox retries keep their receipt identity.
- Chunks are base64 in the JSON payload and capped at 40 KiB decoded (`MAX_FILE_CHUNK_BYTES`), so the 1 MiB control cap is never approached.
- The receiver owns resume: it asks from the first chunk it still lacks, backed by `.alverchat-<id>-resume.part` and its sidecar index. A restarted download resumes; the sender starts from whatever `resume_from` says.
- The file is renamed into place only after the whole-file blake3 hash matches. A mismatch deletes every byte stored for that transfer, so a retry starts clean.
- File frames get no receipt: the protocol answers the `file_offer`, and everything after it is acked by `file_ack` or ended by `file_cancel`. A cancel is advisory and never awaited.
